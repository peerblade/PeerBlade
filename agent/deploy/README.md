# PeerBlade agent deployment

This directory holds the systemd deployment of the Linux agent. Do not run the
commands below on a working VPN server without a maintenance window and a
verified route to the control plane.

## One-command install

An ordinary connection needs neither a hand-built binary nor a hand-written env
file. Open the newly added server in PeerBlade, press **Get the install
command**, copy it and run it on the VPS. Ubuntu and Debian with systemd are
supported, on x86_64 and arm64.

The command downloads the binary and its SHA-256 checksum from the current
control plane, exchanges the one-time enrollment token for a separate agent
token, saves the configuration to `/etc/peerblade/agent.env` with `0600`
permissions and starts `peerblade-agent.service`. Enrollment is valid for
15 minutes and is refused after the first exchange.

The same command also prepares the interface PeerBlade will manage. The panel
puts the server's own name and the default port into the `--endpoint` flag:

```bash
curl -fsSL 'https://my.peerblade.com/install-agent.sh' | sudo bash -s -- \
  --url 'https://my.peerblade.com' --token 'pen_...' \
  --endpoint 'node.example.com:51820' \
  --interface 'peerblade0' --subnet '10.44.0.1/24'
```

Given an endpoint, the installer installs `wireguard-tools`, creates
`peerblade0` on the requested port with `setup-wireguard.sh`, enables IPv4
forwarding, opens the port and the forwarding rule in ufw when ufw is active,
and writes the `PEERBLADE_MANAGED_*` variables into `agent.env`. After it
finishes, the panel can create peers straight away.

The checks that could stop it — a missing package, an occupied UDP port, no
default route — all run before the one-time token is spent, so a host that is
not ready costs nothing. If the port is busy, edit `--endpoint` and re-run.

An interface that already exists is never touched: the installer keeps it,
warns when its `ListenPort` disagrees with the endpoint, and only hands it to
the agent. Interfaces outside `--interface`, `wg0` above all, stay outside
PeerBlade entirely.

To install the agent alone and prepare WireGuard by hand, drop the endpoint or
pass `--no-interface`. The agent then only sends a snapshot of the interfaces
that already exist, and creating a managed one stays a separate step.

Check the installation:

```bash
systemctl status peerblade-agent.service
journalctl -u peerblade-agent.service -n 50 --no-pager
```

The longer manual installation below is kept for development and recovery.

## Reconnecting an installed agent

When a server has been removed from the panel and registered again, the old
agent token no longer works. On the new server's card choose **Reconnect an
installed agent** and run the one-time command on the VPS.

The reconnect script first checks that the installed systemd or Docker Compose
agent belongs to the same control plane. It then updates only
`PEERBLADE_SERVER_ID` and `PEERBLADE_AGENT_TOKEN` and restarts the agent. The
binary, WireGuard and the local state are left alone. An agent belonging to a
different PeerBlade domain is refused.

If the VPS is only temporarily unreachable, there is no need to remove and
reconnect it: PeerBlade keeps the card and shows it online again once the link
recovers.

## Safe removal

The panel offers two different actions. **Disconnect completely** produces a
command that checks the control plane URL and the server UUID, then removes only
the matching systemd service or Docker container and its credentials. After the
command succeeds, the user separately confirms deleting the data from PeerBlade.

**Remove from the panel only** is meant for a VPS that is permanently lost or
already destroyed. It revokes access and deletes the record from PostgreSQL, but
it cannot clean up files on an unreachable server.

The uninstaller deliberately preserves WireGuard interfaces, peers, Docker
volumes and `/var/lib/peerblade-agent`. Disconnecting from the control plane
therefore neither interrupts the VPN nor deletes the local keys of managed
peers.

## Security

The service runs the agent as a dedicated system user, `peerblade`. The only
Linux capability granted is `CAP_NET_ADMIN`, which `wgctrl` needs to manage its
own peers over netlink. The unit further restricts the file system, namespaces,
devices and address families. Client private keys and PSKs are generated by the
agent, stay in `/var/lib/peerblade-agent/peers.json` with `0600` permissions and
are never stored in the control plane.

The secret agent token lives in `/etc/peerblade/agent.env` with `0600`
permissions. The installer never prints the file's contents. Do not commit a
filled-in env file.

## Requirements

- Linux amd64 or arm64 with systemd;
- root access for the installation;
- HTTPS access from the agent to the PeerBlade API;
- the `wireguard-tools` and `iptables` packages;
- a dedicated PeerBlade WireGuard interface;
- Go 1.23+, on the build machine only.

## Building

From the public repository root:

```bash
cd agent
PEERBLADE_AGENT_VERSION=0.6.1 bash scripts/build-linux-amd64.sh
```

The artefacts appear in `agent/dist`:

- `peerblade-agent-linux-amd64`;
- `peerblade-agent-linux-amd64.sha256`.

Check the systemd unit on a machine that has systemd:

```bash
cd agent
bash deploy/verify.sh
```

The version can be overridden:

```bash
cd agent
PEERBLADE_AGENT_VERSION=0.6.1 bash scripts/build-linux-amd64.sh
```

Verify the checksum before copying:

```bash
cd agent/dist
sha256sum --check peerblade-agent-linux-amd64.sha256
./peerblade-agent-linux-amd64 version
```

## Preparing the configuration

Copy the template outside the repository and replace the values:

```bash
cp agent/deploy/agent.env.example /tmp/peerblade-agent.env
chmod 600 /tmp/peerblade-agent.env
```

On a separate server `PEERBLADE_API_URL` must not point at `localhost`: it has
to be a reachable HTTPS URL of the control plane.

Native mode is switched on by the `PEERBLADE_MANAGED_*` variables.
`PEERBLADE_MANAGED_INTERFACE` must name the interface dedicated to PeerBlade and
nothing else. If a new interface is needed, it is safer to start on a port the
current VPN does not use. For example:

```bash
ip route show default
sudo ./agent/deploy/setup-wireguard.sh peerblade0 10.44.0.1/24 51822 eth0
```

Replace `eth0` with the outbound interface from the default route. The script
refuses to overwrite an existing configuration or interface, creates
`/etc/wireguard/peerblade0.conf`, enables IPv4 forwarding and starts
`wg-quick@peerblade0`. After that, open UDP `51822` in the firewall or the VPS
panel and put the public `host:port` into `PEERBLADE_MANAGED_ENDPOINT`.

A node can use any stable DNS name that resolves to it, for example
`node.example.com`. That name goes into every peer configuration as the
`Endpoint`, so changing it later requires reissuing those configurations.

Before running anything with `sudo`, the binary and the configuration can be
checked without touching the system:

```bash
./agent/deploy/install.sh check \
  ./agent/dist/peerblade-agent-linux-amd64 \
  /tmp/peerblade-agent.env
```

## Installing or updating

Copy the binary, `agent/deploy` and the prepared env file to the test server
first. Then, from the root of the copied directory:

```bash
sudo ./agent/deploy/install.sh install \
  ./agent/dist/peerblade-agent-linux-amd64 \
  /tmp/peerblade-agent.env
```

Before stopping the service, the installer checks that the binary is executable
and that the required variables are well formed. A repeated `install` stops the
running service, replaces the binary and the configuration, checks the unit with
`systemd-analyze verify` and starts the service again.

Verification:

```bash
sudo systemctl status peerblade-agent.service
sudo journalctl -u peerblade-agent.service -n 100 --no-pager
```

In the web app the server status should turn `online`, with `lastSeenAt` and
`lastSnapshotAt` refreshed.

## One-time import from wg-easy

Agent `0.4.0+` can safely convert the `wg0.json` of older wg-easy versions into
PeerBlade's own local state. This is a one-time import: after writing it, the
agent never reads wg-easy files again and has no runtime dependency on it.

Always do a dry run first. Without `--write` the command only reads and
validates the server key pair, each client's key pair and PSK, the addresses,
duplicates and membership of the shared IPv4 `/24` network:

```bash
sudo /usr/local/bin/peerblade-agent import-wg-easy \
  --source /path/to/wg0.json
```

The output carries only the server's public key and counters; private keys and
PSKs are never printed. To write, stop the agent, back up its state directory
and pass `--write` explicitly. A non-empty state is not overwritten without an
additional `--force`:

```bash
sudo /usr/local/bin/peerblade-agent import-wg-easy \
  --source /path/to/wg0.json \
  --state-directory /var/lib/peerblade-agent \
  --write
```

Importing the peer state does not by itself move production traffic. For
existing clients to keep working without new configurations, the new WireGuard
interface must preserve the server private key, the server address, the public
endpoint, the listen port and the client addresses from wg-easy. Such a cutover
needs a backup, a short maintenance window and a rollback command prepared in
advance. wg-easy and PeerBlade cannot listen on the same UDP port at once.

## Uninstalling

```bash
sudo ./agent/deploy/install.sh uninstall
```

Uninstalling stops the service and removes the unit and the binary, but
deliberately keeps `/etc/peerblade/agent.env` and the `peerblade` system user.
The configuration with the token, if it should go, is removed by a separate
explicit command after the path has been checked:

```bash
sudo rm -- /etc/peerblade/agent.env
```

## The boundary of control

- without a confirmed control plane command the agent creates and deletes no peers;
- creating, disabling, enabling, issuing a configuration and deleting are available only for peers in PeerBlade's local state;
- a snapshot of third-party interfaces gives PeerBlade no right to issue configurations for them or to delete them;
- the agent does not restart WireGuard and does not manage other panels;
- it changes neither the firewall, the routes, SSH nor Docker;
- it opens no inbound ports.
